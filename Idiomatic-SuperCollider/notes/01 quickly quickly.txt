-   Is this sytactically valid?
    [1, 2, 3] + [0, -1, 0, -1, 1]
    
    -   Yes it is. Before you get angry, keep in mind one of SuperCollider's design philosophies:
    it is a live coding environment. When a singer is performing on stage, no matter what happens
    the show must go on.
    SuperCollider usually tries its best to NOT crash during runtime (the show must go on).
    Hence, operations that would be silly or ill-defined in other languages are sometimes
    (though not always) given meaning in SuperCollider.
    The meaning of the above is that the shorter array is extended modulo itself until it matches
    the length of the longer array, then the binary operation is performed and that is the result
    returned:
        [1, 1, 3, 0, 3]
    But if this makes you uncomfortable there is good news - you can impose discipline on yourself
    and make sure stuff like this does not happen without your knowledge.

What's the deal with "literal" versus "Non-Literal" classes in SuperCollider?

-   The deal is that the syntax for initializing them is generally different.
    In SuperCollider, almost everything is a class (even the integers, floats, etc.).
    This is reminescent of Python and JavaScript if you're familiar with those.
    Literals can simply be initialized from their literals! You know what a literal is...
    -   x = -26;                // literal integer
    -   x = "Hello, world";     // literal string
    -   x = 3.14158;            // literal float
    -   x = 'foo';              // literal symbol
    -   x = [1, 2, 3];          // literal array (though non-literal arrays exist)
    x is an instance of the respective class in each case.
    But there are some classes, such as `Window` where there is no syntactic literal that can be
    used to initialize them (at least the language does not specify such).
    In this case, we initialize objects of these classes by passing the `new` message to the class name.
    -   x = Window.new;
    That's the difference. If the designers of the language so felt inclined they could design
    a literal for this if they wanted e.g. x = w'ABCD'
    But what would be the point of this?


What's your go-to function for a uniformly-distributed discrete random variable in a range of 1 to 10 inclusive?
To put it in English, generate a random integer from 1 to 10 inclusive, where any integer is equally-likely.

-   x = rrand(1, 10);   
    That's it. rrand stands for range random.
    There's also x = exprand(1, 10)
    That one always returns floats, and it implements an exponentially-distributed random variable.

How do you get random floats?

-   rrand can also be used, but the arguments should be written as float literals.
    There are two ways to do this: direct and indirect.
    -   x = rrand(1.0, 10.0);           // direct
    -   x = rrand(a/1.0, b/1.0);        // indirect. Useful in functions for example where a, b are args


Given an array, pick a random item from the array

-   There are two approaches we can use. The first is to use random indexing.
    -   x.at(rrand(0, x.size - 1));
    -   x[ rrand(0, x.size-1) ];
    The second is to use the `choose` method for arrays.
    -   x.choose;
    This turns x into something like a random variable.

FUNCTION DUPLICATION

Just a heads-up in SC.
How do you create an array populated by 100 of random numbers?
You may recall the dup function...

    rrand(1, 10).dup(100);
    rrand(1, 10) ! 100;

This does not work how you'd expect. The left is evaluated first, then the result is used to evaluate the entire statement. All you get is an array of 100 of the same item, where that item is a randomly-picked number.
The solution to this is to duplicate *functions* instead of...function calls, I guess.

    { rrand(1, 10) } ! 100;

The mental model I like to use is that the process is duplicated 100 times and then each process is evaluated and the results are evaluated.
This is just how the language is designed, don't think too hard about it.

LOOPS AND ITERATION
Don't repeat yourself (DRY). Use iteration to kill repetition.
'do' and 'collect' are the heroes of the story.
'do' is like a method. Its argument is a function that tells us what to do for each item in the iteration. 
It is defined for arrays and other collections, but also for integers!

    x.do( ~foo ); // the function can be defined directly as well
    x.do ( { "Hi".postln; } );

That last one is useless since it does not address the items in x. Instead do this...

    10.do( {"Hi".postln;} );


Loop variables: all you need to do is to define an argument for the function. The current item is then passed as the argument.
e.g. 10.do( {arg i; arg.postln;} );

'do' does not modify its receiver, and when you use the 'do' method x.do( ) evaluates to x.
What happens when you supply two args? Is it meaningful? What is the second argument? Try it and take note.

What is 'collect'? Collect is what some 10X programmers would call a "map".

    y = x.collect( {arg i; mapFunc.(i)} );


Note also that we can access index and item by using two function variables e.g.

    y = x.collect( {|i, j|; mapFunc.(i,j) } );

Multichannel expansion
SuperCollider is a bit unusual but that's what makes it so powerful!
The audio is usually not in "mono" by default. This means if you have 2 or 3 or 200 audio channels, you have to tell SuperCollider how to route audio to each of these.
If you say nothing, then the audio simply gets routed to the first audio channel.
On headphones (use with caution!) this sounds like the audio is only coming from the left ear.
One way to expand the audio to another channel, is to use duplication.
Let ugn be a UGen.
    ugn.dup(k) // or ugn ! k
expands the ugn to k consecutive channels, beginning with the lowest-indexed available channel.
If k=2 then this is like basic stereo (it's not stereo since it's not mixed. It's just 2-channel).


LFSaw vs Saw:
The LFSaw is band-limited and designed to run at low frequencies.
Saw is not band-limited.

Changing synth parameters during a synth's lifetime:
The best way to do this is to first define the synth in the body of a function, but declare arguments at the start.
Then we can use the set method. An example is worth a thousand words:

    // sig = SinOsc

x = ~fn.play;
x.set(\freq, 300, \par2, 10, ...);

Why do you need a doneAction?
Every UGen takes up memory on the server. Use s.plotTree to inspect the node tree.
Just because a UGen is not outputting any sound e.g. by generating only zeroes for every audio block doesn't mean it is not consuming memory.
To save memory, SuperCollider allows us specify a doneAction which lets us tell the server what to do with a UGen once it has "finished" generating its signal.
What does "finished' mean, though?
Anyway, the doneAction is specified as a simple integer from 0 upwards.
0 or 2 are the most common.
0 is do nothing, and 2 is free the synth.
You can specify a doneAction as an argument for an envelope e.g.
    env = Line.kr(1, 0, 0.2, doneAction: 2);
There are other doneActions and not all UGens have doneActions.

What is a SynthDef?
I believe it is a more robust way of handling synth function definitions.
The default method is...
    ~fn = {
            arg amp = 1.0, freq = 440.0, phase = 0;
            SinOsc.ar(amp, freq, phase);
        }
Then to play it...
    x = ~fn.play;

We can set arguments dynamically using set method.
x.set(\amp, 0.5);
Do practice with that approach first before worrying about SynthDefs.
